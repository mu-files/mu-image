# Where dng_validate and Core Image differ from the DNG spec

Generated by `muraw/tests/test_dng_opcodes_synthetic.py`; run that module to regenerate this file. Each case writes a small synthetic DNG and compares each renderer with a NumPy port of the DNG spec. mu-image and dng_validate are compared at the stage right after the opcode list; Core Image gives only a final render, so its cell says whether the opcode changes that render the way it changes mu-image's.

Measured with dng_validate, version 1.7.1 (64-bit) and Core Image on macOS 26.5.2.

## Notes

1. At stage 1 (OpcodeList1) on 16-bit data, dng_validate multiplies coefficient c_j by 65535^(j-1) to map raw codes, but the buffer the opcode reads was already divided by 65535 when it was copied to float (`dng_opcode_MapPolynomial::BufferPixelType` and `RefCopyArea16_R32` in DNG SDK 1.7.1). Every coefficient but c1 comes out wrong: c0 is divided by 65535, c2 multiplied by 65535.
2. Core Image does not apply MapPolynomial, in any opcode list. Its render is the same with and without the opcode.
3. Core Image returns an empty image for a 96 x 130 DNG, LINEAR_RAW or CFA; the same data at 256 x 256 renders. The cases therefore use 256 x 256.
4. Core Image returns no image for a float32 DNG, LINEAR_RAW or CFA.
5. dng_validate 1.7.1 rejects an area of all zeros, which the spec reads as the whole image: `dng_area_spec::GetData` clamps the row and column pitch to the area's height and width, 0, and then throws because a pitch is not 1. Camera files write the image bounds instead.
